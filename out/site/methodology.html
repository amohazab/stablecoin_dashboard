How these reports are made

structural risk reports for CDP stablecoins · Amin Mohazab · github.com/amohazab

all tokensrepository

Stablecoin Dashboard publishes structural risk reports for stablecoins backed by collateralised debt positions: what backs each token, how much of that backing can be checked on-chain, and how it holds up under stress. An automated pipeline produces them; this page explains the rules it follows.

Every number traces to a pinned call

Every figure in a report is computed from Ethereum data read at one fixed block. Each value is stored with the contract call that produced it, so anyone can repeat that call on their own node, at that block, and get the same number. An AI model writes the explanatory text around the figures. It never supplies a number: its text is checked against the report's data table before anything is published.

Gates, and why their log is public

A gate is a check that must pass before a report is published. A minor finding publishes with a visible notice; a serious one withholds the report, except where a recorded ruling published a page regardless — the two cases on this site are stated under Open notices. Every time a gate fires, a public log records the date, the token, what kind of check fired, how serious it was, and how it was resolved. Anyone can say their work is checked; a log of checks stopping reports is the evidence. The log below holds 11 entries.

One revision, no hand edits

A report gets one revision. If it fails its checks a second time, the fault is treated as a fault in the template, the rules or the prompts: those are fixed and the report is generated again. No report is edited by hand, and no gate can be switched off for a single run.

Same scenarios, each protocol's own mechanics

The archetype fixes the scenarios so the three pages are comparable; what happens under each shock is modelled from each protocol's own contracts.

Checked by hand

For each token, the analyst repeated a sample of the stress calls through an independent node at the report's block and compared the results with the published artifact. Each token's verify page lists the calls, so you can repeat them too.

Open notices

crvUSD's and GHO's pages were published by a recorded ruling (P-7.11) from their last evaluation run, with the quarantine banner removed and the open notices kept in each page's notices pill; LUSD's page passed every check.

What is not covered yet

The behavioral tier — how the token trades: peg deviation, liquidity, holder concentration and flows — will come from an external monitoring service and is pending.

References such as P-7.11

The appendix pages cite entries such as P-7.11. These are entries in the project's decision log, PROGRESS.md, where every ruling and implementation step is recorded in the order it was confirmed.

Detail for specialists

The six mechanisms behind the claim
  1. One block, one table, one formatter: every contract read in a run carries the run's run_block (rubric 0.5, R-13); every rendered figure replays from a flat-table field (DET-84) and is formatted by one rule (DET-89).
  2. Fail-closed: a missing or erroring gate result means no publication (DET-85, T-25).
  3. Gate integrity: the page embeds the hash of what it was built from; no page publishes with an open Level 2/3 entry, and no override or output-edit resolution exists (DET-13). Pages published by ruling carry their open entries, shown in the table below.
  4. The stale-page banner: "Last successful run / Current run: quarantined", and "Under review" after four quarantined runs (DET-59, memo §8.1.2).
  5. The public log: category-level, one entry per trigger fired (DET-60, memo §8.1.3); this page's row count is checked against the log when the site is built.
  6. Numbers never originate from the model: generate → evaluate → one revision → ship or quarantine; findings patch templates, rubrics or prompts, never a report (brief §6–§7, rubric §6 and 2.2, LLM-01).
